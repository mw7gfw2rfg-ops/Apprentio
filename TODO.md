## Security

- [x] Add basic per-user rate limiting on AI-calling endpoints (draft, interview-prep, employer research) — independent of the tier check, since "premium = unlimited" currently has zero technical ceiling. (Security #2) — Fixed: `claim_ai_rate_limit(action, limit)` SECURITY DEFINER Postgres function (scoped to `auth.uid()`), a fixed-hourly-window atomic `INSERT ... ON CONFLICT DO UPDATE ... WHERE request_count < limit RETURNING`, same shape as `claim_free_draft`. Checked independently of the premium gate at all three call sites: `draftApplication` (action=`draft`, limit 20/hr, checked before the free-draft claim so a rate-limited request doesn't burn a free slot), `generateInterviewPrepQuestions` (action=`interview_prep`, limit 20/hr, covers the Regenerate button since it re-invokes the same action), and `getOrResearchEmployer` (action=`employer_research`, limit 10/hr — lower since it's the most expensive call and self-limiting via the 30-day cache; only checked on the path that actually calls the Anthropic API, not on cache hits). Verified live, not just claimed: at the RPC layer directly, 6 calls against a limit of 5 gave exactly 5 successes (counts 1–5) then a null 6th, with a different action name and a different user both proven independent (unaffected by the first user's exhausted limit). Then end-to-end through the real deployed app: created a real premium test account with a real submitted-stage application, pre-filled its `interview_prep` window to 19/20 via direct RPC, clicked the real "Generate questions" button in the browser — call 20 succeeded with genuine AI-generated content (normal usage unaffected) — then pre-filled a fresh window to exactly 20/20 and clicked "Regenerate" again: rejected instantly in the real UI ("You're sending requests too quickly — wait a bit and try again."), confirmed via direct DB read that the count stayed at 20 (not 21, meaning no Anthropic call fired) rather than trusting the UI alone. (Incidentally caught the fixed-window boundary behavior for real: the first rejection attempt landed exactly on an hour rollover and both the 20th and a stray 21st call succeeded in the fresh window — expected per the documented fixed-window trade-off, not a bug — so the test was redone mid-window to get a clean result.) All test users, applications, vacancy, and rate-limit rows deleted afterward and confirmed gone.

Explicitly did not build the "flag unusual output for review" idea — the existing human-approval gate already covers that role. All test fixtures deleted afterward.
